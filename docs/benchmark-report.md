# 短链服务压测报告

> 版本：V4 | 日期：2026-11-24
> 工具：Apache JMeter 5.6.3 | 环境：单机（应用 / MySQL / Redis / JMeter 同机）

---

## 一、压测目标

验证短链跳转接口 `GET /{shortCode}` 在三种缓存策略下的性能差异：

| 模式 | 说明 |
|---|---|
| `none` | 无缓存，每次请求直接查 MySQL |
| `redis` | Redis 缓存命中直接返回，未命中查 MySQL 并回填 |
| `redis+bloom` | 先过布隆过滤器，再查 Redis，最后回源 MySQL |

---

## 二、环境与配置

| 项目 | 配置 |
|---|---|
| 应用 | Spring Boot 4.1.2 / JDK 25 |
| 数据库 | MySQL 8（localhost:3306），HikariCP 连接池 |
| 缓存 | Redis 7（localhost:6379），Lettuce 连接池 |
| 布隆过滤器 | Redisson `RBloomFilter`（容量 100 万，误判率 1%） |
| 压测工具 | JMeter 5.6.3，命令行模式（`-n`） |
| 数据量 | 约 1,200 条短码 |
| 压测目标 | `GET /google`（302 跳转） |

### 负载参数

| 参数 | 值 |
|---|---|
| 线程数（并发用户） | 100 |
| Ramp-up | 10 秒（逐步启动） |
| 持续时间 | 30 秒 |
| 循环次数 | 无限（由 Duration 控制） |
| 跟随重定向 | **关闭**（只测短链接口本身） |

> **为什么关闭跟随重定向**：短链返回 302 后会跳到目标站点。若 JMeter 跟随跳转，压测流量会打到外部网站，测得的时间也混入外网延迟，结果失真。

## 四、结论

### 结论 1：Redis 连接池是关键瓶颈

Lettuce 连接池 `max-active` 从 **8 提升到 50**：

| 指标 | 池=8 | 池=50 | 变化 |
|---|---|---|---|
| QPS | 8,522 | 13,333 | **+56%** |
| 平均延迟 | 9.77 ms | 6.23 ms | **-36%** |
| P99 | 18 ms | 12 ms | **-33%** |

**分析**：默认 `max-active: 8` 无法支撑 100 并发。请求在连接池排队，成为系统瓶颈。这是配置层面的问题，与业务代码无关，改动成本极低、收益显著。

---

### 结论 2：MySQL 连接池不是瓶颈

在 Redis 池固定为 50 时，HikariCP 连接池 2 / 10 / 50 三档对比：

| 缓存模式 | MySQL池=2 | MySQL池=10 | MySQL池=50 |
|---|---|---|---|
| none | 15,656 | 13,505 | 13,600 |
| redis | 13,333 | 13,409 | 13,175 |

**三档差异均小于 2%，属于压测噪声范围。**

> 注：`A1`（MySQL池=2）的 15,656 为异常点——P99 高达 90ms、最大值 1060ms，说明平均吐吞高但长尾严重，数据不稳定。其余各组稳定在 13,000–13,600 区间。

**分析**：在当前数据量下 MySQL 查询极快，连接数不是约束条件。调大 MySQL 连接池没有收益。

---

### 结论 3：布隆过滤器对「全有效流量」是负优化

| 缓存模式 | QPS | 平均延迟 | 每次请求的 Redis 往返 |
|---|---|---|---|
| redis | 13,409 | 6.20 ms | 1 次（GET key） |
| redis+bloom | 5,230 | 15.94 ms | 2 次（布隆检查 + GET key） |

**加入布隆过滤器后，QPS 下降 61%，延迟上升 157%。**

**分析**：项目中布隆过滤器基于 Redisson 的 `RBloomFilter`，**其判断操作走 Redis 网络，不是本地内存操作**。压测针对的是**一直存在的有效短码**，布隆过滤器永远返回 true，等于白白增加一次网络往返。

> **关键认知**：布隆过滤器解决的问题是「**拦截不存在的短码，避免打穿到数据库**」，而不是「加速已存在的短码」。
> 在**全是无效短码**的场景下，它的收益才会显现（本次未测，见后续计划）。

---

### 结论 4：小数据量下 MySQL 已足够快

`none` 模式（0 次 Redis，只查 MySQL）QPS 为 **13,505**，与 `redis` 模式的 13,409 基本持平。

**分析**：1,200 条短码约 240KB，全部驻留在 InnoDB Buffer Pool 中，索引查询接近纯内存操作。

> **局限**：该结论不可外推到生产环境。当数据量达到百万级、Buffer Pool 无法全部容纳时，MySQL 会因磁盘 IO 显著变慢，届时缓存的收益会明显放大。

---

### 结论 5：缓存显著改善尾部延迟

| 缓存模式 | P99 |
|---|---|
| none | 26 ms |
| redis | 12 ms |

**平均 QPS 接近，但 P99 从 26ms 降至 12ms（-54%）。**

**分析**：缓存的价值不仅体现在吞吐量，更体现在**稳定性**——它消除了一部分慢请求，让绝大多数用户的体验更一致。这比单纯追求 QPS 数字更有业务意义。

## 五、技术要点

### 5.1 为什么外部调用不能放在事务里

`createShortLink` 早期版本带有 `@Transactional`，方法内包含 AI 调用（最坏 4 秒）。数据库连接在方法进入时借出、返回时归还，AI 调用的耗时会长时间占用连接。

**解决方案**：拆出 `ShortLinkWriteService`，事务只包裹 `insert` + `update` 两步行库操作（毫秒级），AI 调用移到事务外。

> **注意自调用失效**：同一个类内 `this.xxx()` 调用带事务的方法不会生效，因为 Spring 事务基于动态代理，内部调用绕过了代理。必须拆成独立 Bean。

### 5.2 为什么 404 要用独立异常

原实现中所有业务异常都抛 `IllegalArgumentException`，被全局异常处理器统一映射为 400。

**问题**：短码不存在属于「资源查找失败」，语义上应为 404，而非「参数格式错误」的 400。混用会导致：

- 状态码错误，客户端无法区分错误类型
- 压测工具的错误率统计失去诊断价值
- 监控与网关的错误分类失真

**解决方案**：新增 `ShortLinkNotFoundException`，单独处理并返回 404。

### 5.3 HTTP 状态码与响应体必须一致

`@RestControllerAdvice` 方法返回对象时，Spring 默认使用 **HTTP 200**。若响应体中写着 `code: 404` 而状态码是 200，压测工具与监控系统看到的全是「成功」。

**解决方案**：在异常处理方法上标注 `@ResponseStatus`，使 HTTP 状态码与响应体中的业务码一致。

### 5.4 AI 调用的降级设计

| 环节 | 失败时行为 | 理由 |
|---|---|---|
| 内容风控 `isSafe` | 返回 `true`（放行） | 无证据证明有害，不应阻断主流程 |
| 摘要生成 `summarize` | 返回 `null`（留空） | 摘要非核心功能，失败不影响创建 |

**关键区分**：`summarize` 失败必须返回 `null` 而非空字符串。`NULL` 表示「未获取」，空字符串是「有效值」，二者语义不可混用。

### 5.5 超时设置

| 位置 | 参数 | 值 |
|---|---|---|
| 连接建立 | `HttpClient.connectTimeout` | 2 秒 |
| 请求响应 | `HttpRequest.timeout` | 2–3 秒 |

两者作用于不同对象，缺一不可。JDK 的 `HttpClient` 默认不设超时，不配置会导致线程无限阻塞。

## 附录：复现方式

```bash
# 压测（命令行模式，避免 GUI 资源占用影响结果）
jmeter -n -t plans/A-clean.jmx -l results/run.jtl

# 生成 HTML 报告
jmeter -g results/run.jtl -o results/report
```

**每种缓存模式测试前必须**：

1. 修改 `application.yml` 中的 `app.cache.mode`
2. **重启应用**（`@Value` 仅在启动时注入）
3. 先执行几次 `curl` 预热缓存（`redis` / `redis+bloom` 模式）
4. 再执行压测
